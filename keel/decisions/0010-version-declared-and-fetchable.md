# 0010 版本声明与版本可获取必须同时成立

> 口径与数据源正文在设计稿 §11.2；本 ADR 只留"为什么这么定"与被否掉的选项。

## 背景

用户发现 Gitee 上 tag 只到 `v3.1.1`，而 `keel/INDEX.md` 的 `keel-version`
已升到 `3.3.3`、CHANGELOG 也写了五节。

**这不是"少了几个标记"**，它让分发渠道最要紧的能力直接失效：

- README 亲口教用户 `install.sh <根> --ref v3.2.0`，而那个 tag 不存在；
- 用户无法固定版本，只能跟着 `main` 走——**"可复现的安装"是分发渠道的底线**。

## 决定

**版本有两处真源，必须同时成立**：

| 真源 | 位置 | 守它的机制 |
|---|---|---|
| 声明 | `keel/INDEX.md` 的 `keel-version` + `CHANGELOG.md` 小节 | 人审（发布关卡） |
| 可获取 | 发布仓的 `vX.Y.Z` tag | **CI 检查**（本 ADR 新增） |

CI 新增「版本号与 tag 一致」：`keel-version` 声明了但 `git rev-parse v<版本>` 不存在即 fail，
并打印修法。**声明与可获取从此一起验。**

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 只在 README 写"最新版本是 v3.x" | 文档解决不了拉取失败；用户要的是**固定版本可用** |
| 让 `install.sh --ref` 拉不到时回落到 main | **更坏**：用户以为固定了版本，实际拿到别的代码，且无从察觉 |
| 把 tag 维护写进 §12.3 的人工清单 | 核实过：**§12.3 从头到尾没提过 tag**——不是"写了但漏做"，而是**根本没意识到需要**。这比漏做更值得记：缺的不是执行，是规格 |

## 后果

- **好处**：`--ref` 从"README 里的建议"变成"可用且会失败得响亮的能力"。
  不存在的 ref 现在报错并列出可用版本，而不是装上别的东西。
- **代价**：发布流程多一步（打 tag + 推 tag），且 tag 推漏了 CI 会红。
  这是有意的摩擦——**它拦的是"看起来发布成功了"这种静默失效**。
- **风险**：annotated tag 推拉在镜像同步时可能有延迟（Gitee→GitHub 约 3–4 分钟，
  §12.3 已记录）。CI 只查本地 tag 是否存在，不受影响。

## 沉淀

**"版本号写对了"不等于"版本能用"。**
声明（文档/字段）与可获取（tag/产物/接口）必须**一起验**——
这两者脱节时，一切看起来都正常：CI 绿、文档全、版本号对，只是用户装不到那一版。

> 与 ADR 0008 的蒸馏段同源：凡是"靠人记得做"的清单，第三次就该变成机器检查。
