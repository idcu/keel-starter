# 0007 兑现 MCP 落点（只读服务），并把语义检索做成"接入位"

## 背景

两处长期悬空的承诺：

1. §4.2 表里写着"支持 MCP 的客户端 → 把 INDEX + NOW 暴露成 MCP resource"，但**从没有实现**。
   而 §4.3 自己承认：无 shell 环境下"没有任何机制能阻止它多读"——MCP 正是那个机制，却没有；
2. 检索只有 `grep`，召回停在关键词级。这是内核零依赖换来的代价，但**评测里这是最短的板**，
   而当时既没有补法，也没有说明"为什么故意不补"。

## 决定

- **MCP 只读服务**：`checks/mcp/keel-mcp-server.py`（python3 标准库 + stdio JSON-RPC 2.0），
  暴露 `keel://index`、`keel://constitution`、`keel://now` 三个资源；只读、无写操作；自带 `--self-test`；
- **边界写死**：不进 `keel-lint.sh`、不进 §9.1 检查面，§9.3"内核零依赖"前提不变；
- **检索增强做成接入位**（§9.5）：语义检索（Serena 等）走 MCP 声明接入，
  由 `checks/check-mcp-config.sh` 校验"声明不落空"（能解析 + command 在 PATH），
  **恒 exit 0**——没装不是缺陷，接不接入是团队决策。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 把 MCP 服务写进内核依赖 | 内核必须能在无 python3 / 无网络的机器上跑，否则 §9.3 承诺作废 |
| 让 MCP 服务支持写入（直接改 NOW.md） | 写回是 §10.3 的**人/AI 流程**，不是协议动作；开了写口就绕过了阻塞表与归档约定 |
| 给 check-mcp-config.sh 定 fail 级 | "没接 Serena"不是项目缺陷，判死会制造大规模假告警（§9.4 同一教训） |
| 索性不补语义检索，只在文档里承认短板 | 承认短板但不给接入路径，等于把问题留给每个使用者各造一遍 |

## 后果

- 好处：§4.2 的那一行从"设计稿承诺"变成"可运行组件"；短板有了**指定的**补齐路径，而不是各人自选。
- 代价：MCP 服务引入 python3 依赖（与自测套件同一条底线，且属**可选**组件，不装不影响任何既有能力）；
  stdio 服务需客户端侧配置，配置错会静默不生效——这正是 `check-mcp-config.sh` 要拦的那种病。
- 自证方式：`--self-test` 8 项 + CI 一步，避免"组件写了但没人知道它坏没坏"。
