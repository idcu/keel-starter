# 0002 入口规格进入机器验：keel-version / project-state 必填，锚点按原文检查

## 背景

v2 把"先点火"列为 P0 却没有任何检查——整套系统的开关交给了自觉；
根 INDEX 缺 keel-version / project-state 也无从判死。同类问题成片：
"写了规则却没写检查"，属于声称强制、实则空转（v3 一次补进 7 项，见 §9.1 注）。
规则只要不能被脚本判死，就等于建议。

## 决定

根 INDEX.md frontmatter 强制 `keel-version` 与 `project-state` 两字段（值域见 §5.2）；
§4.1 点火锚点必须在 CLAUDE.md / AGENTS.md / .cursorrules / .cursor/rules/keel.mdc
中出现原文，改写即 fail。两者均进入 keel-lint 检查范围（§9.1-10）。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 保持 v2：规则写在文档里，靠自觉执行 | 实测空转，且文档腐烂无人知，比没文档更危险 |
| project-state 放独立文件 | 破坏"唯一必读入口"，必读文件数与固定成本同时上升 |
| 锚点只写不检查 | 锚点是整套系统的开关，开关不能交给自觉 |

## 后果

- 好处：入口三样（协议 / 路由 / 状态）与点火开关全部可判死。
- 代价：升级方必须补 frontmatter、装锚点；锚点文案自此冻结——
  改文案等于同步改 §4.1 原文、lint 常量与各仓库锚点三处。

## 修订 · v3.13.0：从「入口机器验」扩到「判据机器验」

背景：入口已被判死，但「判据自己有没有被判死」仍靠人记。2026-11-04 的账本工作实测出两处
账目不一致，且都不会让任何判据变红——`test-lint` 自报「48 用例 + 2 元检查」，实际另有
`DOC` / `LOCALE` / `PROSE` 三个元检查未进分母；DESIGN §9.3 散文写「39 例 fail」，实测 38。

决定：新增 `checks/verify/checks-ledger.py`，把 §9.1 的 19 项判据登记为单一真源，
覆盖状态从 `test-lint.py` 的 `CASES` 自动推导；`verify-report.json` 必须含 `checks_ledger`，
三档之和必须等于 19。分母固定 19，同时单列「按已实现 18 项」与 auxiliary/meta，
禁止只报百分比。

| 被否掉的选项 | 为什么没选 |
|---|---|
| 用一份手写 `coverage.tsv` | 手工标注必然腐烂，且与 test-lint 形成双源 |
| 把 §9.1-15 补成机器判据 | 它是项目扩展位；内核补判据会引入第二套真源 |
| 分母混入元检查与动态套件 | v3.13.0 当时的判断：分母混类会让覆盖率失去意义。**v3.14.0 已修正**：元检查补了判死用例后并入分母并单列口径；动态套件仍不进（它们不是判据） |

后果：账本能证明「有用例」，不能证明「用例有效」；后者留给变异测试。
低覆盖率是结论，不是缺陷。

## 修订 · v3.14.0：分母不再只数 §9.1

v3.13.0 的分母只有 19 条编号，`DOC` / `LOCALE` / `PROSE` 三个元检查失败只计
`bad`、不进分母——检查会红，但覆盖率看不见它；而且它们只跑干净输入，没有反例。

- 三条元检查各补一条判死用例（`META_CASES`：坏脚本副本 / `LC_ALL` 泄漏赋值 /
  旧版本 README），进入「含元检查」分母；`§9.3-BUDGET` 因用例 20 已判死，给正式编号。
  分母 19 → 22（含元检查）→ 23（含预算检查），三个口径同屏打印。
- `§9.1-15` 仍不给编号：它没有判死用例，补机器判据会制造第二套真源。
  **给不了判死用例就不登记**——这是 §9.1-15 的教训，不是本轮新增的偏好。

## 修订 · v3.14.0：清单绑定 provenance（判据之外的一层）

账本证明「判据有负例」，但不回答「这份清单是哪份代码跑出来的」。旧清单可以冒充新证据。

- `verify-report.json` 增 `provenance`：`commit`、`dirty` / `dirty_files`、
  四个判据文件（`keel-lint.sh` / `test-lint.py` / `checks-ledger.py` / `verify.py`）的
  `sha256`、平台、locale、`generated_at`。
- `check-verify-report.py --repo <发布仓>`：commit ≠ HEAD、自称干净却有未提交文件、
  sha256 已变，三种都 FAIL；`release.sh --apply` 在推送前跑同一条命令。
  `--selftest` 用真 git 仓库加 4 条负控（11 → 17）。
- 诚实边界：只证明「清单与代码自洽」，不证明可信；**刻意不写「防篡改」**——
  自洽的假清单随时能造，没有外部核对就不上升。
