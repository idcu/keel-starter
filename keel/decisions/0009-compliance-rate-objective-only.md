# 0009 遵守率只测客观事实，不采信 AI 自述

## 背景

§11 已有三个度量指标（返工率 / 坑复发率 / 平均阻塞时长），但它们全部度量**项目**。
没有一个数度量 **AI 本身**——它到底有没有真的遵守 Keel 的规则。

而这才是整套系统的最终目的：Keel 存在的意义是"让 AI 以恒定成本拿到正确上下文并照做"，
若 AI 拿到上下文却不照做，前三个数再好也说明不了问题。

2026-10 联网调研（逐个**读源码**，非读 README）确认：

| 项目 | 体量 | 它的"遵守率" | 判定 |
|---|---|---|---|
| `jackeyunjie/dsh-rule-lens` | 1485 行 JS / 3 提交 / 零测试 | 面板标题写"遵守率"，数据结构里**只有拦截计数、没有分母** | **语义是反的** |
| `fuwasegu/aegis` | 41k 行 TS / 989 测试 | 生成的 adapter 规则第 5 步原文是 "Self-Review" | **自报 = 不可验** |
| `holaOS` | 48 万行 TS，生产级 | 全仓 grep 遵守率 → 零实现 | 干脆没做 |

**结论：没有任何项目真正实现了这个指标。** 空白是真的。

## 决定

**遵守率 = 1 − (命中检查项的轮次 / 总检查轮次)**，两个数据源都是客观的：

```
violations.jsonl   ← lint 的 ❌/⚠️ 命中 + 提交时 git diff 触碰的受限路径
load.jsonl         ← 每轮必读 INDEX+NOW 的实际字节数（load-estimate.sh 已有）
```

**关键：这两个文件都不来自 AI 的输出**，而来自文件系统与 git 历史——**AI 一个都改不了**。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 直接问 AI"你遵守了吗"，解析它的自述 | **holaOS 的取证已经证明这条路会产出更精致的形式合规**：门禁全部正确触发、AI 对 `src/client/` 零编辑、然后宣布完成；加重门禁措辞后情况更糟。自报数据不仅不可靠，还会因为过于体面而失去诊断价值 |
| 沿用 dsh-rule-lens 的口径（数拦截次数） | 它没有分母。加载 10 条违反 1 条 → 拦截 0 次 → 显示"0 次拦截"，读起来像 100% 遵守。**数字方向是反的**，比没有数字更危险 |
| 让 AI 自报"Self-Review"（aegis 的做法） | 同第一项。本质是把度量权交给被度量者 |
| 靠 MCP 记录 AI 读了什么来推断遵守 | 读到 ≠ 照做。加载量已经在 §7 管住了，不构成新信息 |

## 后果

- **好处**：这是本项目目前**唯一有可能做出差异化**的度量。
  调研确认全赛道无人实现，而 Keel 的三件套（lint + pre-commit + commit-msg）**本来就全是客观的**，
  缺的只是一个把三者输出聚合成带分子分母的数字的聚合器——工程量不大，概念壁垒高。
- **代价 1**：只能测"可被脚本判死"的规则。若某条规则 §2 原则 4 判死不了，
  它就不进分母——**这会反过来逼着人把规则写成可判死的**，是好事，但一开始会暴露一批"假规则"。
- **代价 2**：需要额外两个 jsonl 的存储与聚合逻辑，属于新代码面，要计入 §7 的预算审视。
- **风险**：目前**没有真实用户数据**，遵守率会长期是空序列。
  一个没有基线的指标最容易变成自欺欺人的数字——所以本 ADR 只定口径与数据源，
  **不承诺何时能给出真实数字**。

## 沉淀下来的一条反直觉发现

来自 holaOS 的取证（`docs/research/context-governance-verify.md` 全文）：

> **点名失败模式，AI 就精确复现那个失败模式。**

即在规则里写"不要犯 X"，反而提高了犯 X 的概率。

**这一条直接改变了本项目的写作规范**：坑条目的「正解」段必须写**具体动作**，
不能只写"不要那样做"。这不是文风问题，是有效性问题。
